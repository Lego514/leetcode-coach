# 設計上的決定

這個 App 幾個關鍵的選擇，還有每個選擇放棄了什麼。每一項分四段：遇到什麼問題、選了什麼、沒選什麼、代價是什麼。各部分怎麼接在一起，見 [Architecture](architecture.md)（英文）。英文版：[decisions.md](decisions.md)。回到 [README](../README.zh-TW.md)。

## 1. 資料先存在瀏覽器，再用待上傳清單同步

- **問題**：
  - 練習常常是零碎的時間，而且多半在收訊不好的手機上，例如健身組間的微複習。
  - 從履歷連結點進來試用的人不該需要帳號。
  - 免費的伺服器會睡著。
- **選擇**：
  - 每次寫入都先寫進瀏覽器的資料庫（IndexedDB，用 Dexie），同一個交易裡加一筆到待上傳清單。
  - 登入只是多了同步：一個 `POST /api/sync` 把清單送上去，同時拉回這台裝置上次之後有變的東西。
- **沒選**：
  - 以伺服器為主、離線時用快取：每次寫入都要網路，伺服器睡著就卡住。
  - Firebase 這類現成的同步服務：程式比較少，但同步的做法正是我想弄懂的部分。
- **代價**：
  - 資料格式有兩份：瀏覽器的資料庫和 Postgres，要一直保持一致。`shared/protocol.ts` 的 zod schema 就是兩邊的約定。
  - 瀏覽器的資料庫有怪問題：iOS 上用 key cursor 的查詢會丟「Unable to open cursor」，所以改成整張讀出來再處理。

## 2. 每筆紀錄保留最新的那次修改

- **問題**：兩台裝置可能在離線時改到同一筆紀錄。
- **選擇**：
  - 每筆紀錄帶著最後修改的時間。伺服器只收比較新的修改；被拒絕的修改，伺服器會連同自己那份一起送回去。
  - 刪除會留下記號，所以比較舊的修改不能把刪掉的紀錄救回來。
  - 版本號來自 Postgres 的 sequence，同一個使用者的同步一次只跑一個（advisory lock），所以拉資料時不會漏掉任何一筆修改。
- **沒選**：
  - CRDT 或逐欄合併：同時改也不會掉資料，但程式和儲存都多很多。
  - Version vector：能偵測衝突，但偵測到以後還是要有人決定留哪個。
- **為什麼這樣就夠**：
  - 一個帳號就是一個人用。
  - 大部分紀錄根本不會衝突：每次練習、模擬面試、微複習的答案都有自己的 UUID，只會新增、不會修改。
  - 真的會衝突的只有會改的紀錄，例如筆記、設定和白板。
- **代價**：
  - 兩台離線的裝置改了同一篇筆記，只會留下比較晚的那次。
  - 「比較晚」是看各台裝置自己的時鐘，時鐘不準的裝置可能會蓋掉不該蓋的修改。

## 3. 複習排程是算出來的，不同步

- **問題**：如果把排程存起來同步，兩台裝置離線練習時會各算一份，其中一份會被蓋掉。
- **選擇**：
  - 練習紀錄才是真正的資料。一題的排程是照時間順序重播它的練習紀錄算出來的（`rebuildProgress`）。
  - 改了排程的算法，就加一版 Dexie 的 upgrade，全部重播一次。
- **沒選**：把排程當成一般紀錄同步。比較簡單，但剛好在上面那種情況會掉資料。
- **代價**：
  - 會影響排程的寫入，都要在同一個交易裡重算那一題，包括：
    - 練習紀錄。
    - 模擬面試：講解會影響「Easy」和「已熟練」。
    - 自己新增的題目：它們有自己的目標時間。
  - 重播的結果每次都要一樣。例如「標記以前刷過的題」會把分散開的天數存在紀錄上（`delayDays`），每台裝置才會重播出同一天。

## 4. FSRS-6，再加上這次練習的證據

- **問題**：
  - FSRS 的預設參數是從記憶卡來的：卡片想得很辛苦，還是代表你記得。但寫題需要提示，通常代表有一部分已經忘了。
  - 自己按的四個選項也看不出這題寫得順不順。
- **選擇**：
  - 照公式自己寫 FSRS-6，再用幾百組隨機的複習紀錄跟官方的 `ts-fsrs` 比對。
  - 在上面加這次練習的權重：花的時間跟題目目標時間比、提示看到第幾層、卡在哪裡。
  - 寫得不順的題一週內再確認一次。
  - 畫面上的「為什麼隔這幾天」跟排程用同一份程式，說明不會跟實際行為對不上。
- **沒選**：
  - SM-2 或固定間隔：比較簡單，但不管隔了多久。
  - 原本的 FSRS：需要提示才寫出來的題，會排得太遠。
- **代價**：權重是我自己判斷的，不是從資料算出來的。複習紀錄夠多以後，下一步是像 FSRS 的 optimizer 那樣從資料擬合這些權重，並檢查預測的記得機率跟實際結果對不對得上。細節見 [Review scheduling](scheduling.md)（英文）。

## 5. 網頁放 Cloudflare，API 留在 Render

- **問題**：Render 免費方案的伺服器閒置 15 分鐘就睡著，第一次打開要等 20 到 60 秒。連網頁本身都要等，但資料存在瀏覽器的 App 根本不需要伺服器就能打開。
- **選擇**：
  - Cloudflare Worker 送出建置好的檔案，`/api/*` 轉給 Render，cookie 和轉址照轉。
  - 網頁和 API 在同一個網域（coach.legoli.dev），所以 cookie 是自己網站的、也不用處理 CORS。
  - 使用者的 IP 放在 `x-forwarded-for` 轉給 Render，因為次數限制要用。
- **沒選**：
  - API 也搬到 Workers：伺服器用了 Node 的套件（Postgres 的驅動、scrypt、web-push），也是用 Node 測試，搬過去等於重寫。
  - Render 付費、不會睡的方案：不用等了，但每個月都要付錢。
  - 網頁和 API 用不同網域：要處理 CORS 和第三方 cookie，Safari 會擋第三方 cookie。
- **代價**：
  - 要部署兩個地方，API 也多經過一站。
  - 伺服器睡著時，登入、同步和 AI 照樣要等，但 App 本身馬上就能打開。

## 6. 白板一個房間一個 Durable Object

- **問題**：一起編輯需要一個地方替同一個房間的修改排好順序、保存白板，沒人用時就結束。
- **選擇**：
  - 每個房間是一個 Cloudflare Durable Object，同一個房間的訊息在同一個地方一個一個處理，不用鎖。
  - 用戶端送小小的修改：放上一個元件、刪掉一個元件、換掉步驟。房間用 zod 檢查、照順序套用，改了兩秒內存檔。
  - 用 WebSocket 的休眠功能，沒人用的房間不花錢。
  - 最後一個人離開 7 天後，房間就刪掉。
- **沒選**：
  - 在 Render 上開一台 WebSocket 伺服器：會睡著，而且所有房間擠在一台上。
  - Yjs 或 Liveblocks 這類現成的服務：同時修改合併得比較好，但又多一個依賴、多一種資料格式。
- **代價**：
  - 同時修改是以元件為單位決定的：兩個人同時拖同一個陣列，後到的那個贏。
  - 房間綁在 Cloudflare 上。

## 7. 只能看的連結是算出來的，不另外存

- **問題**：模擬面試的面試官要能看白板、不能改；而且從只能看的連結不能推回能改的連結。
- **選擇**：
  - 只能看的代碼是房間代碼的 SHA-256 雜湊，取 24 個字。
  - 伺服器用只能看的代碼替 Durable Object 命名，所以兩種連結都連到同一個房間。
  - 能不能改，看連線是從哪個路徑進來的（`/room/` 或 `/view/`），用戶端自己送的東西一律不算數。
- **沒選**：隨機產生一個只能看的代碼，存在房間裡。也行，但要儲存，而且每次連線都要多查一次。
- **代價**：
  - 只能看的連結不能單獨撤銷，要撤銷只能開新房間。
  - 有能改連結的人算得出只能看的連結。這沒關係，能改本來就比能看的權限大。

## 8. 使用者自己的 AI 金鑰不會送到我們的伺服器

- **問題**：共用伺服器上的 AI 回饋要花錢，所以只給名單上的帳號用，每天有次數上限（預設 20 次）。其他人也應該能拿到回饋。
- **選擇**：
  - 可以貼上自己的 Anthropic、OpenAI 或 OpenRouter 金鑰。金鑰只存在這個瀏覽器的 localStorage，不進待上傳清單，不會送到我們的伺服器，也不會出現在你的其他裝置上。
  - 由瀏覽器直接呼叫 AI 服務。
  - 提示詞、輸出格式和整理輸出的程式都在 `shared/ai.ts`，伺服器和瀏覽器用同一套標準評分。
  - 沒有金鑰的人，可以把提示詞複製到自己的 ChatGPT 或 Claude，再把回覆貼回來。
- **沒選**：把金鑰送到我們的伺服器、由伺服器去呼叫。這樣我們就變成保管別人秘密的人。
- **代價**：
  - 網站上執行的任何程式都讀得到 localStorage，所以金鑰的安全跟整個頁面的安全一樣。React 會跳脫畫面上的文字，Content-Security-Policy 只讓網站自己的程式執行（不能用 inline script、不能 eval），頁面也只能連到幾個已知的網址。但打包進來的套件如果有惡意程式照樣會跑，所以金鑰不像放在伺服器上那麼安全。
  - 從瀏覽器呼叫 AI 服務也要服務那邊允許，例如 Anthropic SDK 的 `dangerouslyAllowBrowser`。
